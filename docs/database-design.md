
# Database Design

## 1. Overview

The application uses PostgreSQL to persist URL mappings. This ensures that short URLs remain available after the FastAPI server restarts.

**Database:** `url_shortener`

**Table:** `urls`

## 2. Table Structure

| Column | Data type | Purpose |
|---|---|---|
| `id` | `BIGINT` | Unique identifier generated by PostgreSQL |
| `original_url` | `TEXT` | Destination URL |
| `short_code` | `VARCHAR(6)` | Six-character code used for redirection |
| `created_at` | `TIMESTAMPTZ` | Record creation timestamp |

### Schema

```sql
CREATE TABLE urls (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    original_url TEXT NOT NULL,
    short_code VARCHAR(6) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_urls_short_code_length
        CHECK (LENGTH(short_code) = 6)
);
```

This represents the intended schema established by the project's migrations.

## 3. Constraints

### Primary key

`urls_pkey` enforces uniqueness of `id` and prevents it from being NULL.

### Unique constraint

`urls_short_code_key` ensures that two records cannot have the same short code.

This protects the mapping between a short code and its destination.

### Check constraint

`ck_urls_short_code_length` requires every short code to contain exactly six characters.

The database rejects invalid values even if an application-level validation check is bypassed.

### NOT NULL constraints

`original_url`, `short_code`, and `created_at` must contain values.

## 4. Why Is `original_url` Not Unique?

Multiple short codes may point to the same destination.

For example:

| Short code | Original URL |
|---|---|
| `Ab12Cd` | `https://example.com/` |
| `Xy34Zk` | `https://example.com/` |

This is valid behavior. Therefore, `original_url` does not require a unique constraint.

## 5. Indexing

PostgreSQL automatically creates indexes for primary-key and unique constraints.

The `short_code` unique constraint creates an index that supports efficient lookups:

```sql
SELECT original_url
FROM urls
WHERE short_code = 'Ab12Cd';
```

The application uses this query when redirecting a user.

An index can improve lookup performance, but PostgreSQL chooses the execution plan based on the query and available statistics. Small tables may use a sequential scan.

Inspect the query plan with:

```sql
EXPLAIN
SELECT original_url
FROM urls
WHERE short_code = 'Ab12Cd';
```

## 6. Transactions

A transaction groups database operations into a unit of work.

- `COMMIT` makes changes permanent.
- `ROLLBACK` undoes uncommitted changes.

The application uses Psycopg connection contexts to manage transactions. If an exception escapes the transaction context, the transaction is rolled back.

## 7. Connection Pooling

The application uses `psycopg_pool.ConnectionPool` to reuse database connections.

Current configuration:

- Minimum connections: `2`
- Maximum connections: `10`
- Pool opens during application startup.
- Pool closes during application shutdown.

Pooling avoids creating a new database connection for every request. It also limits the number of connections used by each application process.

The pool's maximum is per process, not necessarily the maximum across the entire deployed application.

## 8. Database Migrations

Alembic manages changes to the database schema over time.

Migration files are stored in `migrations/versions/`.

The current migration history contains:

1. **Baseline migration:** Creates the initial `urls` table on a fresh database.
2. **Short-code constraint migration:** Adds the constraint requiring exactly six characters.

### Useful commands

Check the current revision:

```bash
python -m alembic current
```

View migration history:

```bash
python -m alembic history
```

Apply pending migrations:

```bash
python -m alembic upgrade head
```

The project uses `python -m alembic` to run Alembic through the active Python environment.

**Important:** `stamp` records a migration revision without executing that migration's SQL operations. Use it only when the database schema already matches the revision being recorded.

## 9. Verification Queries

Run these commands inside `psql url_shortener`.

Check the number of stored mappings:

```sql
SELECT COUNT(*) FROM urls;
```

Inspect the table structure:

```sql
\d urls
```

Inspect constraints:

```sql
SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'public.urls'::regclass;
```

Find records with invalid short-code lengths:

```sql
SELECT id, short_code
FROM urls
WHERE LENGTH(short_code) <> 6;
```

The last query should return zero rows.

## 10. Design Decisions

- **Persistent storage:** PostgreSQL stores mappings beyond the lifetime of the application process.
- **Unique short codes:** The database protects against duplicate codes, including concurrent requests.
- **Six-character codes:** Both the application and database enforce the code-length requirement.
- **No uniqueness on destination URLs:** Different short codes can map to the same destination.
- **Connection pooling:** Connections are reused rather than recreated for each request.
- **Versioned migrations:** Schema changes are tracked and can be applied to new environments.
